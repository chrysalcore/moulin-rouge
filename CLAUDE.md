# molino_rojo (frontend) — notas específicas de este repo

Preferencias generales en `~/.claude/CLAUDE.md` (que cubre solo lo transversal a todos los proyectos). Esto es lo propio de este repo.

- `tsconfig.json` tiene `"strict": true` (decisión de Ordnay, 2026-08-08 — ya no es la excepción del portafolio). `target` se subió de `es5` a `es2020` en el mismo trabajo, porque `es5` rompía el typecheck real (iteración de `Set` en `useConnect.tsx`) apenas `tsc` empezó a correr de verdad. Activar `strict` solo destapó dos errores, ambos en `useConnect.tsx`: el tipo de retorno declaraba `Dish[] | undefined`/`Event[] | undefined` cuando `data` nunca es `undefined` en runtime (`useStatus` lo inicializa como `{dishes: [], events: []}` y el reducer nunca lo deja indefinido) — se corrigió la anotación, no la lógica.
- Arquitectura de estado en capas, no tocar sin entenderla primero:
  - `src/context/dataContext.tsx` → `DataProvider`/`useData`: datos ya cargados (`categories`, `dishes`, `events`).
  - `src/hooks/useStatus.tsx` → reducer local para estado de fetch (`loading`/`data`/`error`), acciones tipadas como unión discriminada en `src/types/state.ts`.
  - `src/hooks/useConnect.tsx` → compone `useStatus` + efecto de fetch, devuelve tupla etiquetada.
  - Todo hook custom que combine estado sigue el patrón de tupla (`[loading, data, error]`), no objeto.
- Tipos centralizados en `src/types/*.ts`, re-exportados por el barrel `src/types/index.ts` — importar siempre desde `'../types'`, nunca del archivo específico directo.
- Único repo con comentarios en el código: un banner de una línea en español al inicio de cada archivo de `src/types/` (ej. `// Tipos para el estado y reducer`). Mantener ese patrón si se agregan archivos de tipos nuevos; no extenderlo al resto del código.
- Único repo que adoptó Conventional Commits (`feat(scope): …`, `chore(scope): …`), pero solo a partir de la migración a TS; commits previos son descriptivos sin prefijo, igual que el resto del portafolio. Decisión confirmada por Ordnay (2026-08-09): se mantiene solo en este repo, no se extiende al resto del portafolio ni se revierte acá.
- CSS global por sección en `src/assets/styles/*.css`, BEM (`form-field__input`), sin CSS Modules.

**Fase 2 — Unit hooks con DOM (`renderHook`) (hecho 2026-08-09):**
- `useConnect`: mock de `load` (`vi.mock` a la factory, no automock), `vi.useFakeTimers()` + `vi.advanceTimersByTimeAsync(3000)` para cruzar el `setTimeout` de 3s y esperar la promesa mockeada en el mismo paso. Cubre: estado inicial (loading, arrays vacíos, error null), transición a `SUCCESS` (loading false, dishes/events/categories con el payload, dedup de categorías), transición a `ERROR` (loading false, error poblado, data vacía). El primer intento del test de dedup usaba fixtures sin categoría repetida (`buildDishes()` ya trae `pizza`/`hamburguesa` distintas) — pasaba igual con o sin `[...new Set(...)]`, o sea no probaba nada real; se corrigió agregando un tercer dish con categoría repetida y se confirmó rojo al romper el dedup a propósito antes de darlo por bueno.
- **Guard `ignore` del efecto (`if (!ignore) dispatch(result)`), discutido con Ordnay, no testeado a propósito:** en `pokedex-app` el mismo patrón se testea forzando dos fetches superpuestos (una respuesta "stale" que resuelve después de una más nueva), porque ahí el efecto se re-dispara con cada búsqueda/página y cada request puede devolver datos genuinamente distintos. Acá el efecto de `useConnect` corre una sola vez por montaje real (`deps: [dispatch]`, nunca cambia) — la única forma de forzar una segunda ejecución en tests es `React.StrictMode` (monta→desmonta→remonta sincrónicamente en dev), pero ambas ejecuciones pegan siempre a la misma URL fija: en producción devolverían el mismo dato, nunca uno viejo distinto del nuevo. Se armó un test forzando datos "stale" vs "fresh" divergentes a propósito para poder ponerlo en rojo, y Ordnay señaló que esa divergencia es artificial — no representa ningún bug real de este hook tal como está escrito hoy. Se descartó por esa razón (no por imposibilidad técnica de probarlo). Revisar si conviene testearlo si el efecto llegara a re-dispararse con algún parámetro en el futuro (ej. filtro/búsqueda, como en pokedex).
- `DataProvider`/`useData`: `renderHook(() => useData(), { wrapper })`, mismo patrón que el resto de los hooks de Fase 1/2, no un componente que renderiza DOM. Primer intento equivocado: usar `DishesList` (consumidor real de producción) montado con `MemoryRouter`, para evitar un componente de prueba artificial — pero eso terminó testeando el renderizado de `DishesList` (headings, filtro de categoría) en vez de la plomería del contexto, mezclando el alcance de Fase 2 con el de Fase 3. **Hallazgo importante (2026-08-09, discutido con Ordnay) — el plan original de `errorElement` NO cubre el bug real encontrado:** el fix documentado originalmente (ruta intermedia sin `path` agrupando `Home`/`Reservations`/`Menu`, con su propio `errorElement`, dentro del árbol que cuelga de `<Outlet/>`) solo atrapa errores de render que ocurren *dentro* de esas rutas hijas. El crash real de `dishes.map` ocurre en `useConnect`, llamado por `Main`, que `App` renderiza **directo en su JSX, no a través del `<Outlet/>`** — está "arriba" de esa ruta intermedia en el árbol, así que su `errorElement` nunca lo va a ver. Para cubrir ese caso puntual con un `errorElement` haría falta ponerlo en la ruta raíz (la de `App`), pero eso vuelve a pisar `Header`/`Hero`/`Footer` ante cualquier error — el trade-off que el plan original quería evitar.

**Decisión final (2026-08-09):**
1. **Arreglar la causa raíz en `load.ts`, no parchear con el boundary:** validar que la respuesta de `axios.get` sea efectivamente un array (`Array.isArray`) antes de armar el `SUCCESS` — si no lo es, tratarlo como error (mismo camino que hoy toma un `catch`, con un `ErrorPayload` propio, ej. `{ message: 'Unexpected response shape' }`). Con esto, `dishes.map` en `useConnect` deja de poder recibir algo que no sea un array — el bug real queda cerrado en su origen, no encubierto.
2. **Igual se implementa el Error Boundary de la ruta intermedia**, como red de seguridad genérica para errores de render en `Home`/`Reservations`/`Menu`/`DishesList` que no tengan que ver con el fetch (ej. un bug futuro no relacionado). Fix: **no** una clase `ErrorBoundary` envolviendo `<Outlet/>` en `App.tsx` — el proyecto ya usa `createBrowserRouter` (React Router v7, data router), que trae `errorElement` para esto. Ruta intermedia sin `path` agrupando `Home`/`Reservations`/`Menu`, con su propio `errorElement`, mantiene `Head`/`Header`/`Hero`/`Footer` intactos y solo reemplaza el contenido del `Outlet`.
3. **El fallback del `errorElement` NO lleva botón Reload** (a diferencia del componente `Error` del fetch). Discutido con Ordnay: un error de *render* suele ser determinístico — si el bug está en el código o en la forma de un dato específico, reintentar exactamente el mismo render vuelve a explotar igual; un botón "Reload" ahí sería decorativo y generaría una falsa expectativa de recuperación automática. En cambio, el fallback lleva un mensaje claro + un link explícito a Home (`Link to={''}`) como salida segura — redundante con la nav del Header que ya queda viva, pero explícito en vez de depender de que el usuario se dé cuenta solo.
- Test primero (debe fallar contra el código actual): montar el árbol de rutas reales (`routes` + `createMemoryRouter`) forzando un throw de render en `Home` (mockear el módulo `../../components/pages/Home` para que tire), verificar que el layout persiste (`Header` con su botón "Reserv" sigue visible) y que aparece el mensaje + link a Home en el área del `Outlet`. Implementación después: la ruta intermedia + `errorElement` en `AppRouter.tsx`, hasta que el test pase.
- Si aparecen gaps similares en Fases 1-2, mismo criterio: test rojo primero, fix después, aviso en el momento.
